# [vendor:codex] Восстановление desktop Voice: передача в agentops

[README](../../README.md) · [Индекс](../../docs/INDEX.md) ·
[CHANGELOG](../CHANGELOG.md) · [TASKS](../TASKS.md)

**Владелец сопровождения — agentops.** Sergey 17.11 прямо попросил Voice
завершить инспекцию и передать восстановление desktop-приложения и
подключения SSH на обслуживание agentops. Voice сохраняет факты и
предлагаемый короткий порядок, не меняет глобальные правила или чужой repo.

## Проверенный случай

Voice не запускался: `Failed to load worklet module script` для
`app://-/assets/workers/realtime-buffered-audio-worklet.b5db4cfc.js`.
На mac-work установлен `/Applications/ChatGPT.app`, bundle ID
`com.openai.codex`, версия `26.1103.31037`, build `25241`.
Файл с точным хешированным именем есть в app.asar, 3937 байт.
В app logs ошибка `AbortError`, стадия `MICROPHONE_SETUP`; точная причина
отказа загрузчика не установлена. Это не доказанное отсутствие файла.

Проверена фактическая команда главного процесса:

```text
/Applications/ChatGPT.app/Contents/MacOS/ChatGPT --proxy-server=http://127.0.0.1:8389 --disable-quic
```

Прокси отвечал HTTP401 на запрос OpenAI API без авторизации — транспорт
доступен; это не ошибка пароля прокси. Именованный alias в просмотренных
профилях не найден, не выдавать эту команду за найденный alias.

По прямому поручению Sergey процесс приложения `36363` завершён SIGTERM
после проверки executable/argv и запущен снова:

```sh
open -a /Applications/ChatGPT.app --args \
  --proxy-server=http://127.0.0.1:8389 --disable-quic
```

Новый PID `68671` проверен с теми же флагами. Обновления приложения,
удаления кэшей/профилей/истории и рестарта демона на VDS не было.
После запуска VDS-чаты перестали отображаться. Native read-only RPC
нашёл все13неархивированных чатов; существующий daemon на VDS продолжал
работать с прежним PID. Sergey вручную включил настройку подключения
удалённого хоста, после чего чаты вернулись. Точное название включённой
галки в UI не зафиксировано — не придумывать его.

Проверка после восстановления: пришла правильная голосовая реплика
«Проверка связи», затем Sergey сообщил, что голос работает.

## Предлагаемый первый шаг при повторении того же симптома

1. Предупредить Sergey **до перезапуска**, что SSH-подключение desktop к
   VDS может потребовать повторного включения в настройках приложения.
   Это его явная просьба, пока автоматическое восстановление не доказано.
2. Подтвердить главный процесс, его владельца, bundle и текущие proxy-флаги.
   Не переиспользовать старый PID; параметры выше — факт17.11, а не вечная
   константа. Быстро проверить локальный прокси. Новое подтверждение уже
   разрешённого обычного перезапуска не требуется.
3. При этой конкретной ошибке сначала полностью перезапустить desktop с
   сохранением проверенных параметров и сразу попросить одну тестовую
   голосовую фразу. Не начинать с большого расследования Whisper/SIP,
   квот, переустановки или очистки пользовательских данных.
4. После старта проверить подключение сохранённого SSH-хоста `ufohosting`
   в Settings → Connections → SSH и видимость прежних VDS-чатов. Если
   исчез список, не объявлять историю потерянной и не создавать замены:
   сначала проверить native thread/list и состояние подключения клиента.
5. Готовность означает реальный входящий текст и слышимый пользователем
   ответ. Если повторный запуск не помог, тогда читать свежий узкий
   app-log по ошибке и сравнивать bundle/версию, не удаляя кэши вслепую.

## Что принять agentops

- Принять сопровождение короткого восстановления в существующую
  процедуру/skill harness и найти или оформить однозначный launcher.
  Не подменять его новым постоянно работающим сервисом без нужды.
- Проверить поддержанный способ автоматического подключения уже
  сохранённого SSH-хоста после запуска; не обещать автоматику заранее.
  Не редактировать внутренние DB приложения без схемы/бэкапа/проверки.
- Пока автоподключение не принято, включить предупреждение и ручную
  проверку подключения в checklist каждого такого restart.
- Done: воспроизводимый restart с сохранением прокси, восстановление
  списка тех же чатов и живой голосовой smoke; источник процедуры и
  обратные ссылки обновлены владельцем.

Официальные источники, проверены17.11:
[диагностика и app logs](https://learn.chatgpt.com/docs/reference/troubleshooting),
[remote SSH](https://learn.chatgpt.com/docs/remote-connections),
[desktop deep links](https://learn.chatgpt.com/docs/app/commands).
Настройки SSH открываются `codex://settings/connections/ssh`. Ссылка
`.../ssh/add?name=...` **добавляет** хост и по документации выключает
автоматическое подключение добавленного хоста; не применять её как
безусловный reconnect существующего хоста. Поддержанный API/toggle для
автоматического подключения в этой инспекции не установлен.
