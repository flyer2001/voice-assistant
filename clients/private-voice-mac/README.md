# Пилот голосовых уведомлений на Mac

[Спецификация и план](../../specs/private-voice-channel.md) · [Проект Voice](../../README.md)

Один клиент воспроизводит короткие актуальные уведомления. Он принимает
локальные события от тестового источника и привязывает аудиоочередь к
заданному устройству. При смене выхода уже начатое воспроизведение
прекращается. Пропущенное событие остаётся доступно в исходной сессии
и не возвращается в плеер после подключения гарнитуры.

## Запуск теста

Соберите пакет на Mac из каталога этого README. Запускать плеер нужно
в графической сессии пользователя, например в её Terminal.

```sh
swift test
swift build
.build/debug/private-voice-mac route
.build/debug/private-voice-mac listen /tmp/voice-pilot-inbox '<UID наушников>'
```

Используйте UID из `route`, когда системным выходом выбрана знакомая
Bluetooth-гарнитура. Встроенный выход Mac допускает нейтральный тон.
В отдельном терминале можно отправить одно тестовое событие:

```sh
.build/debug/private-voice-mac submit /tmp/voice-pilot-inbox "$(uuidgen)" 'test-session' --tone
```

Вместо `--tone` можно передать тестовый файл с 16-битным PCM mono 16 кГц
без контейнера, не длиннее 30 секунд. Пробное событие живёт 10 секунд.
Повтор того же идентификатора в текущем окне доставки подавляется.
Клиент потребляет временные файлы, журнал пишет статус и ID события.
`played` означает завершение воспроизведения по данным клиента.

Плеер принимает `pause`, `resume`, `off` и `quit` из локального терминала.
События из inbox изменять эти настройки не могут. Для проверки громкой
связи на известном встроенном выходе передайте его UID, числовой `source`
из `route` и флаг `--force-test` после UID наушников. Команды `force` и
`interact` включают и продлевают разрешение. Этот режим работает только
для встроенного синтетического тона. При неизвестном порте выводится
лишь нейтральный сигнал. Свойства текущей аудиоочереди описаны в
[документации Apple](https://developer.apple.com/documentation/audiotoolbox/kaudioqueueproperty_currentdevice).

## План подключения

1. Проверить сборку, правила и локальную доставку на Mac. Отключение
   Shokz во время воспроизведения проверено. Для обычной речи на
   динамиках ещё нужно проверить остановку при блокировке Mac с force.
2. Подключить одну тестовую сессию через существующий транспорт. Доверенный
   адаптер подтверждает источник и срок события, дожидается разрешённого
   выхода, затем синтезирует звук. Локальный JSON-inbox пилота принимает
   подготовленное аудио и служит границей теста, а право посылать туда
   данные ограничено локальным аккаунтом.
3. Провести пробу с двумя сессиями, проверить повторы, одновременные
   события и переключение устройства. Для телефона добавить независимую
   проверку аудиомаршрута на самом клиенте. После приёмки общей интеграции
   подключать остальные сессии через общий интерфейс.

## Проверено 26 ноября

Восемь тестов правил прошли на Linux и macOS. Сборка на рабочем Mac
доставила синтетическое событие через локальный inbox и завершила
воспроизведение с привязкой к Shokz. Повтор события и просроченное
событие были пропущены. Повтор прогона с неподходящим UID не запускал
звук. Эти проверки использовали отдельный временный запуск.

За шесть секунд простоя без уведомлений клиент использовал около
0,33% одного ядра и 14 МиБ памяти процесса на Mac. Это короткий
диагностический замер с заблокированным аудиовыходом.

## Проверено 27 ноября

Сергей отключил Shokz во время синтетической озвучки новым клиентом.
Журнал показал остановку при переходе на встроенные динамики и возврат
к Shokz. Сергей услышал сигнал только в наушниках. После подключения
старое уведомление не возобновилось.
