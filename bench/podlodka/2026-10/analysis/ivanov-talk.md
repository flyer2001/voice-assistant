## Тезисы

1. **Узкое место переехало из кода в понимание, что делать** [06:30]. Инженер
   теперь делает работу PM, system design, ревью, прод — и строит фабрику.
2. **Качество агента ограничено архитектурой и входом** [09:00]; агент копирует
   окружение, поэтому плохое мультиплицируется [11:00]. Техдолг «за две недели
   вместо полугода» — тезис без замера.
3. **Определение** [11:30]: фабрика производит софт по стандартам, получая на
   вход только продуктовую инструкцию.
4. **Две проблемы** [13:30]: делать правильные вещи (DoR + база знаний) и делать
   вещи правильно (гайдлайны + обязательный system design + верификация).
5. **Фабрику не покупают, её строят под свой value stream** [42:30], итеративно,
   разбирая инциденты [43:00].
6. **«Фабрика, по сути, набор документации; главное — контекст»** [64:00].
7. **Детерминированное — в хуки**, проза в CLAUDE.md с ростом контекста
   забывается [58:30-59:00].

## Оснастки и механизмы контроля по частям

### Вход: «делать правильные вещи»

- **Шаблон тикета** [17:00]: user story (роль, возможность, результат), список AC,
  in scope / out of scope, контекст (RFC, связанные тикеты, проект, дизайн),
  проект и приоритет.
- **Гейт Definition of Ready** [15:30]: фабрика проверяет каждый входящий тикет;
  если чего-то нет — пишет в тикет вопросы «1, 2, 3».
- **Снятие неоднозначностей** [19:30-20:30]: поиск по базе знаний (Notion, может
  быть Confluence и т.п.), только по документам подсистемы; самопроверка «хватает
  ли информации»; нет — статус **Blocked on User** и вопрос человеку. «AI не
  угадывает».
- **Продуктовая база знаний** [20:30-21:30]: продукты, как работают, биллинг,
  тарифы, отчёты, онбординг продавцов; плюс доменные документы в репозитории.
  Без неё «не работало».
- Обновление базы знаний — полуавтоматическое ревью раз в месяц, автоматически
  ответы из тикетов в Notion не попадают [46:30-47:30].

### Исполнение: «делать вещи правильно»

- **Архитектурные гайдлайны на компонент** [22:30].
- **CLAUDE.md как указатель** [23:30-24:30]: кратко проект и стек, доменная
  терминология, справочные доки и когда их читать, внешний контекст (Linear,
  Notion, доки вендоров API), список ADR «чтобы агент не повторялся»,
  антипаттерны, правила, которые часто ломаются. Остальное подгружается по мере
  надобности.
- **Антипаттерны** [26:00-27:00]: запрет `forwardRef` в NestJS, запрет
  преждевременного выноса общих модулей («нужно доказательство переиспользования»).
  Правило: каждая повторная фигня агента → запрет в файле.
- **Обязательный system design на каждый тикет** [23:00, 27:30-29:00]: агент пишет
  документ (подход и почему, файлы, модель данных, схема БД и индексы, Mermaid),
  кладёт в приватный gist, человек комментирует, ревизии до approved. «Агент
  никогда не пишет код, пока дизайн не утверждён» [27:00].
- **Откат на любую стадию** разрешён [29:30].
- **Хуки** вместо прозы для детерминированного [58:30].

### Проверка результата

- **Агент не проверяет себя** [35:00]: оркестратор читает CLAUDE.md, код пишет
  субагент, внутреннее ревью — субагент, верификатор и тестер — отдельные.
- **Тесты в worktree** [36:00-37:30]: unit и интеграционные без общего стенда;
  локальный Postgres с копией стейджинга; обязательная проверка миграций (было:
  в main слили миграции, локально не применены — «ничего не работает»);
  интеграционные в контейнерах (S3-мок, Valkey; DynamoDB выкинули); UI в браузере
  через Chrome DevTools; вердикт + скриншоты.
- **Проверка наличия доказательства** [40:30-41:00]: после случаев «всё работает»
  при неподнявшемся приложении проверяется, что результат верификации есть и в PR
  есть скриншоты успешного выполнения. Детерминированно или агентом — не сказано.
- **Внешнее ревью PR** [31:30-32:00]: Claude ревьюит открытый PR, фабрика сама
  отвечает на комментарии, «как минимум критические».
- **Человек**: ревью своего PR каждым инженером + кросс-ревью по round-robin

## Как бизнес-требование становится задачей

1. Требование рождается у человека: инженер или product owner пишет тикет руками
   в Linear [56:30-57:00]. «Factory никогда не пишет тикеты».
2. Исключение: для крупной работы (пример «15 тикетов») он пишет документ «что и
   как делаем», просит Claude нарезать тикеты в Linear с ограничениями
   («краткие») и ревьюит их [57:00].
3. Требование живёт в тикете; Notion — источник продуктового контекста [57:30].
   Расхождение тикета и Notion — фабрика «обычно» задаёт вопрос; если нет — «сделаю
   фигню, пойму и пойду исправлять Notion» [58:00].
4. Дальше гейт DoR → вопросы → system design → код → проверки → PR → люди.
5. Сроки: «все вопросы бизнеса о сроках переехали на сторону бизнеса» —
   разработчики спрашивают, когда будут доступы, банк, юр. документы
   [52:00-53:00, 53:30-54:30]. Бизнес в workflow фабрики не включён: «стартап,
   бизнес занят маркетингом» [64:30].
