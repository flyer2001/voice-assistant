## Сл. 5. 4 способа дать агенту руки

Сетка 2×2: столбцы **фронтенд · браузер** / **бэкенд · API**, строки **как задумано** / **в обход**.

| | фронтенд · браузер | бэкенд · API |
|---|---|---|
| как задумано | **01 агент-пользователь** — ходит по сайту как человек, решает на каждом шаге | **02 официальный API** — API · MCP · CLI с авторизацией |
| в обход | **03 скрипт по селекторам** — Playwright / скрипт в консоли по фиксированному пути | **04 неофициальный API** — снимаем запросы из Network, притворяемся браузером |

Карточка каждого способа: анимация отправки письма в Gmail, оценка точками (из 3) и плюсы-минусы.

| Способ | скорость | дёшево | устойчивость | без бана | + | − | Пример / пометка |
|---|---|---|---|---|---|---|---|
| 01 агент-пользователь | 1 | 1 | 3 | 2 | не нужны токены и настройка, переживает редизайн | медленно и жрёт токены | ЭЦП в Точке: в API подписи нет, в браузере её подтягивает расширение |
| 02 официальный API | 3 | 2 | 3 | 3 | быстро, стабильно, легально | бывает очень дорого, нужных методов может не быть | gh, Google Calendar MCP |
| 03 скрипт по селекторам | 2 | 3 | 1 | 1 | быстро и без LLM на каждом шаге | самый хрупкий: падает от любого редизайна | не советую |
| 04 неофициальный API | 3 | 3 | 2 | 1 | быстро, дёшево, умеет всё, что умеет клиент | серая зона: таймауты, риск бана | ЛК $30 vs API $2000/мес — куки обновляют сами скрипты |

Тексты в анимациях:
- 01: «🤔 ищу «Написать» → 🤔 где поле «Кому»? → ⌨ ввожу адрес → ⌨ пишу тему → ⌨ пишу текст письма → 🤔 где «Отправить»? → ✓ отправлено · **7 LLM-шагов**».
- 02: `agent · MCP: gmail`, «# публичный API, документированный контракт», `gmail.send_message(to, subject, body)` → `{ "status": "sent", "id": "msg_18f3c2a9" }`, «✓ **1 вызов · 0.4 c**».
- 03: `[data-testid=compose]`, `$ node send.ts`, «✓ отправлено · **1.1 c**», затем «✗ [data-testid=compose] not found», «после редизайна: TimeoutError».
- 04: DevTools → Network → `POST _/gmail/send` → «Copy as cURL» → агент в терминале шлёт `POST /_/gmail/send` с `Cookie: SID=…` → `200 { "op": "SEND_OK" }`, «⚠ недокументировано · ToS».

## Сл. 7. Мой сетап | Codex vs Claude Code

Схема «верхний уровень» над «движком». Фазы:
1. Codex: верхний уровень — **Codex CLI** (терминал), **Codex Desktop** (треды · automations · браузер), **VS Code extension** (чат в редакторе); движок — **Codex App Server**. Что оболочка докидывает в движок: «+ тулы · скиллы: developerInstructions, create_thread, read_thread_terminal, automation_update, skill: in-app browser, открытые файлы IDE». Стрелки: «↓ тулы, скиллы, контекст — в ядро», «⇡ ядро вызывает функции оболочки».
2. Codex vs Claude Code — несовпадающие сущности:
   - треды Codex ≠ сессии Claude
   - automations ≠ routines · cron
   - in-app browser ≠ claude-in-chrome
   - `~/.codex/skills` ≠ `~/.claude/skills`
3. bb сверху: «треды, автоматизации, браузер, скиллы, плагины»; снизу движки — Codex, Claude Code, Pi, OpenCode, у каждого «+ тулы · скиллы».

## Автономность и принятие решений
- Ты сам автономно идешь до результата, пока путь **ожидаемый**. Если уперся в неожиданную проблему – не нужно скрытно костылить воркэраунд. - Не проси пользователя сделать то, что можешь сделать сам доступными инструментами; просьба к нему - последний ресурс, с причиной, почему сам не смог
- Если пользователь недоволен результатом skill или спрашивает о его процессе, предложи обновить skill

Do you own judgment. В случае, где предположение имеет большую цену ошибки – имеет смысл его проверить. Например, часто при проектировании системы полезно делать небольшие временные спайки для проверки гипотез.

## Один путь и быстрый отказ в реализуемых системах
- **Никакой бл*ть fallback-логики, деградированных режимов, запасных парсеров, вторичных промптов или альтернативных модельных путей**, если это явно не запрошено или не одобрено. Считай каждую такую ветку архитектурной сложностью, а не безобидной страховкой
- Предпочитай поиск unified правила и архитектуры вместо множества workaround-ов вокруг частных случаем

## Definition of Done и скоуп
- Если скоуп неоднозначен, уточни; не добавляй незапрошенные "nice-to-have" фичи.
- Я очень не люблю оверинжиниринг. Если систему можно сделать проще/элегантнее/идиоматичнее без потери функциональности, делай проще.
- Если видишь, что какую-то сложность можно убрать – предлагай это
- Иногда бывает, что новый функционал не ложится нормально в существующую архитектуру. Тогда нужно не делать воркараунды, а сделать архитектурные изменения. (объясни почему, получи одобрение)
- Аномально легкий или быстрый успех - повод заподозрить тихий no-op, а не радоваться

## Технологии и инструменты
- Основное: Python, TypeScript/JS. Современные идиомы; type hints в Python, strict types в TS.
- **Инструменты проекта важнее.** Следуй существующим паттернам/скриптам; не мигрируй toolchain без запроса.
- Дефолты для новой/ad-hoc работы: Python (3.13) -> `uv` (не pip/poetry); проектный/локальный JS/TS -> `bun` (не npm/yarn); глобальные npm CLI -> `npm install -g`.
- Ad-hoc Python: всегда `uv run` (никогда bare `python`/`python3`), Python 3.13, PEP 723 inline metadata - и для сохраненных скриптов, и для stdin-сниппетов (`uv run - <<'PY'`). Объявляй third-party deps в заголовке, не избегай их; ephemeral `uv` deps для анализа/инспекции нормальны (глобальный cache, без загрязнения проекта). Stdlib-only только когда это явно проще.
- Ad-hoc JavaScript/TypeScript: всегда `bun --install=force run` (никогда bare `node`), включая stdin-сниппеты (`bun --install=force run - <<'TS'`). Для self-contained скриптов объявляй third-party deps обычными imports (`import { z } from "zod"`): Bun сам скачает их в глобальный cache, `package.json` не нужен. Пин версии в спецификаторе (`"zod@4.1.5"`) НЕ скачивает произвольную версию: работает только latest или версия, уже лежащая в глобальном кеше, иначе ENOENT — на другой машине такой скрипт упадет. Нужна воспроизводимая конкретная версия — делай package.json.
- ts (bun) предпочтительнее чем python (uv). python – если нужны специфичные библиотеки

## Сл. 14. Мои скиллы | Foreman (прораб)

Скачать: `foreman.zip`.
- **проблема:** «Много агентов — глухой телефон. Один — теряет контекст.»
- **решение:** «Исполнитель компактится — прораб помнит и следит»

Три схемы:
1. **много агентов:** менеджер (X · Y · Z) → фронт (X · Y), бэк (X), тестер (Y · ?), ревьюер (?). «глухой телефон на каждом стыке».
2. **один исполнитель:** контекст → «↓ компакция» → после — «потеряно: требование, решение, грабля». «компакция выкидывает важные детали».
3. **прораб — умная модель** (держит: цель, требования, решения, приёмка; «компакций 0») → «бриф ↓», «⏱ проверяет по таймеру ↓», «↑ отчёт» ← **исполнитель — модель попроще** (tool calls, логи, браузер, дампы; компактится он).

## Сл. 15. Мои скиллы | Learn

Скачать: `learn.zip`. Кнопка-переключатель «улучшить систему ↗» → «v2 · eval».
- **проблема:** «Люди не знают, как они работают на самом деле»
- **решение:** «Учимся на практике: сессия → правила → скилл»; во второй фазе — «Не ждём новую задачу: replay ≈ eval»

Схема: «как я думаю, что работаю» (шаг 1 → шаг 2 → шаг 3) против «как работаю на самом деле» (? ? ?).
Цикл: сессия (агент крутится в цикле, ■ твои подсказки) → `/learn` → `SKILL.md` (— правила, — грабли, — проверки) → запуск: новая задача по скиллу → ✓ / «нашли косяк → обновить».
v2: «replay той же задачи», «сабтред · чистый контекст» → прогнать → починить → «≈ eval».

### subagent-review-loop

> description: "Use when the user wants a dedicated subagent to review code, plans, or remediation proposals critically, then keep an iterative review dialogue with that same subagent until the proposed fixes are explicitly approved."

- Один ревьюер-**субагент** с чистым контекстом (`fork_context: false`), **тот же** на все раунды. Нельзя его пересоздавать, нельзя заводить параллельных ревьюеров без просьбы.
- Главный агент классифицирует замечания: accept / partially accept / reject. Принятые превращает в план, отправляет план тому же ревьюеру. Повторяет до `fully approved`. «The main agent owns the technical judgment», «Do not blindly trust the reviewer».
- Вердикт бинарный: `fully approved` / `not approved` + только blockers. Blocker узкий: корректность, соответствие спеке, runtime safety, обещанный workflow. Optional hardening, стиль и nice-to-have тесты блокерами не считаются.
- Для артефактов по внешним требованиям: версионированный «review contract» (бизнес-цель, требования со ссылкой на источник, одобренные сокращения). Менять его можно только с согласия пользователя.
- Готовые промпты ревьюеру. Первый: «Review this artifact critically. Do it yourself and do not delegate…».
- Провайдер ревьюера в скилле **не задан**.

### foreman

> description: "Режим прораба – ты держишь цель и high-level vision, а всю работу руками делает ОДИН исполнитель (субагент / sub-thread), которого ты направляешь, наблюдаешь, корректируешь на ходу, докидываешь ему следующие задачи и принимаешь результат сам. Любые задачи — код, ресёрч, browser use, данные. Use when the user asks to be a manager/менеджер/прораб над одним исполнителем или в ситуациях, когда работа предполагает много контекста, важного для конкретных шагов, но не важного для движения по задачи в целом (множественные действия в браузере, изучение конкретных деталей какой-то системы и т.д.)."

- Руками прораб делает только три вещи: читает результаты, гоняет короткие проверки для приёмки, пишет свои заметки. «Уровней два. Не заводи „менеджера под собой“».
- Модель: «Дефолт – исполнитель на один уровень модели слабее прораба (**Fable -> Opus, Astra -> Sol, Sol -> Terra** и т.д.)».
- Требования пользователя переносить в бриф **дословно**: «Самый частый глухой телефон возникал в самом прорабе, когда он пересказывал». В брифе — «что, а не как»: механизм, придуманный прорабом, — гипотеза.
- Протокол исполнителя: вопрос — конец хода; самоотчёт раз в **15–20 мин**; финал — итог + доказательство; после компакции перечитать бриф.
- Пробуждение: событие исполнителя + **таймер** через планировщик харнесса, ровно один будущий тик. Интервал: активная работа **10–15 мин**, долгий прогон **30–60**, ожидание пользователя — тика нет. Блокирующее ожидание и фоновый `sleep` таймером не считаются.
- «Правило тишины»: каждое пробуждение заканчивается одним из трёх состояний: исполнитель работает / готово / ждём пользователя.
- Приёмка: «Отчёт исполнителя — гипотеза», проверять наблюдаемый результат на реальном окружении.
- Разрешения: исполнитель в `auto`. Прораб сам одобряет запросы в рамках мандата (`allow_once`). Прод, sudo, отправку секретов наружу, платежи и push в default-ветку — нет.
- Смена исполнителя — только в пяти случаях, в том числе «после компакции он дважды выдумал факты».
- Харнессы: bb — sub-thread; Claude Code — фоновый субагент + SendMessage + CronCreate; Codex — нативные субагенты или треды.

### learn

> description: "Turn a completed or substantially progressed agent session into a reusable executable workflow and persist the hard-won knowledge in the right artifact. Use when the user invokes /learn or $learn, asks to extract lessons or patterns from the current session, wants a shareable process another agent can execute from scratch, or wants an existing skill or instruction updated based on what worked."

`agents/openai.yaml`: display_name «Learn», short_description «Извлекает переиспользуемый процесс из сессии».

- Сессия — сырьё, а не структура: восстановить идеальный путь для свежего агента, провалы превратить в правила и проверки, без хронологии.
- «One session is one sample»: каждое правило помечается **firm** или **provisional** (`(provisional: <evidence>; revisit if <signal>)`).
- Если контекст компактился — читать транскрипт сессии выборочно (`~/.codex/sessions`, `~/.claude/projects`, `~/.pi/agent/sessions`).
- Цель записи: обновить скилл, проектную инструкцию, новый скилл или Markdown-плейбук, если процесс сырой. Механику написания скиллов отдаёт нативному `skill-creator`.
- Перед записью — четыре вопроса пользователю: куда сохранить, какие решения обобщать, валидировать ли (ничего / структурная проверка / **replay**), сохранять ли задачу как eval.
- Eval-кейсы — в `evals/evals.json` формата skill-creator. Replay: свежий агент только с артефактом решает ту же задачу в изолированной песочнице, без подсказок об ожидаемом результате; повтор до прохождения.
