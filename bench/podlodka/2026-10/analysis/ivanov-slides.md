## Verbatim

### Старый процесс (сл. 11, итог сборки 4-11)

PM приносит проект → Дизайнер рисует экраны → Разработчики оценивают → Дизайн
утверждён → Разработка → QA заводит баги (пунктир «баги» обратно в Разработку) →
Фиксы + приёмка PM → Релиз.

### Инструменты по этапам (сл. 13)

- Исследования, рассуждения и документы -> ChatGPT, Claude, DeepSeek
- UI-дизайн -> Claude Design
- Код -> Codex, Claude Code, Pi, OpenCode
- Тестирование -> то же самое + playwright/chrome dev tools mcp

«У каждого этапа старого процесса теперь есть AI-инструмент. Узкое место
сместилось.»

### Работа инженера: раньше → сейчас (сл. 14)

| Обязанность | Раньше | Сейчас |
|---|---|---|
| Писать код | большая часть дня | делегировано фабрике |
| Писать тесты | после кода | их пишет фабрика, ты сверяешь с AC |
| Уточнять требования | работа PM | твоя работа: тикет и есть спецификация |
| System design | сеньоры, крупные фичи | каждый тикет, ты его утверждаешь |
| Code review | PR коллег | PR агентов, и их намного больше |
| Дебаг продакшена | да | всё ещё да, и без AI в 3 часа ночи |
| Строить фабрику | – | новая работа |

Сл. 15 «Что остаётся инженерам?»: System Design, **Factory Engineering** (крупнее
всех), Acceptance Testing, Product Management.

### Почему архитектура всё ещё важна (сл. 16)

- Человек должен понимать, дебажить и владеть системой без AI
- Инциденты не ждут агента: прод лежит, ты читаешь код
- Налоги и комплаенс: поток данных аудитору объясняешь ты, а не модель
- AI копирует то, что видит. Чистая структура на входе, чистый код на выходе
- Архитектурные доки это контекст фабрики. Плохой дизайн тиражируется в масштабе

### Матрица (сл. 21)

### DoR-чеклист (сл. 24)

«DoR (Definition of Ready) должен подтвердить:
1. Есть user story и acceptance criteria
2. Есть in-scope и out-of-scope
3. Заданы проект и приоритет»

Схема: DoRCheck → «все 3 на месте» → Ready; «чего-то не хватает» →
BlockedOnUser → «человек ответил» → обратно в DoRCheck.

Сл. 23: для правильной реализации нужно 1) понимать продукт, 2) понимать скоуп,
3) снять неоднозначности.

### Шаблон тикета (сл. 25)

```
## User story
Как <роль>, я хочу <возможность>, чтобы <результат>.
## Acceptance criteria
- [ ] Дано <состояние>, когда <действие>, тогда <результат>
- [ ] ...
## In scope
- ...
## Out of scope
- ...
## Контекст
Страница в Notion, связанные тикеты, дизайны
```

### Пример тикета, который проходит DoR (сл. 26)

```
## User story
Как оператор платформы, я хочу PDF-выписку DAC7 для каждого
подотчётного продавца, чтобы отправить её до 31 января.
## Acceptance criteria
- [ ] Дано: отправленный отчёт DAC7. Когда я нажимаю
      «Сгенерировать выписки», тогда для каждого подотчётного
      продавца создаётся один PDF
- [ ] Суммы по кварталам в PDF совпадают с отправленным отчётом
- [ ] Продавцы без подотчётной активности выписку не получают
## In scope
- Генерация PDF, скачивание ZIP-архивом со страницы отчёта
## Out of scope
- Рассылка выписок продавцам по email (отдельный тикет)
- Выписки по 1099-K
```

### Что фабрика спрашивает в ответ (сл. 27)

```
Проверка DoR: 1 открытый вопрос
В AC написано «один PDF на подотчётного продавца».
Продавец может быть подотчётным в 2 странах ЕС.
-> Один PDF на продавца или один на продавца на каждую страну?
Искал в Notion «DAC7 reporting»: ответа нет.
Тикет поставлен на паузу: blocked_on_user
```

### Снятие неоднозначностей (сл. 28)

- Он не угадывает. Он спрашивает.
- Сначала ищет в базе знаний
- Только потом задаёт вопрос человеку
- Тикет встаёт в blocked_on_user и освобождает фабрику для другой работы

Схема: Открытый вопрос → «Ответ есть в Notion / доках?» → да: «Использовать,
сослаться на источник»; нет: «Спросить человека в треде тикета» → «Пауза:
blocked_on_user».

### База знаний (сл. 29-30)

1. Описания продукта в Notion
2. Короткие доменные доки в репозитории для агентов, со ссылками на Notion
3. Фабрика ищет там, прежде чем отметить пробел или задать вопрос

Схема: **Notion** («источник правды, правит команда») → `docs/domain/*.md`
(«кратко, для агентов») → Фабрика → «Проверка DoR + дизайн»; Notion → Фабрика
также напрямую через «search API».

### Слои документации (сл. 33-35)

Сл. 33:
- CLAUDE.md / AGENTS.md: один файл, **до 150 строк**, загружается всегда
- conventions.md, architecture.md: читаются по необходимости
- ADR: почему мы выбрали то, что выбрали
- Антипаттерны: «на этом мы реально обжигались»

Пирамида: CLAUDE.md «загружается всегда» → architecture.md · conventions.md
«читать перед изменением области» → ADR «читать перед дизайном, который может им
противоречить» / Антипаттерны «больше никогда не предлагать».

Сл. 34 «Что внутри CLAUDE.md, в этом порядке»:
1. Проект: сервисы и стек, 5 строк
2. Доменная терминология: одно слово на одно понятие
3. Справочные доки: что читать и когда
4. Внешний контекст: Linear, Notion, доки вендоров, с триггерами
5. Антипаттерны: реальные инциденты, больше никогда
6. Короткий список конвенций: 5 правил, которые ломаются чаще всего
7. Сборка / тесты: точные команды для проверки

Сл. 35:
- architecture.md: технологический стек; Medallion-пайплайн: bronze, silver,
  gold; модули и инфраструктура; общие паттерны: events vs commands, company
  scoping, actor context, слои.
- conventions.md: код — «сначала прочитай, потом пиши; не перекомментируй»;
  обработка ошибок — «доменные ошибки, без catch-and-rethrow»; тестирование;
  безопасность.
- «ADR: 10 принятых, читать перед любым дизайном, который может им противоречить».

### Антипаттерн, как он записан (сл. 36)

```
## Anti-patterns — concrete
We have actually been bitten by these. Do not propose them again.
- **`forwardRef` to break a NestJS cycle.**
  Extract shared logic into a third service.
- **Pre-emptive `*.factory.ts` / interface-with-one-impl.**
  Two duplicates is fine. Extract on the third real pattern.
- **Mocking the Postgres database in integration tests.**
  Hit `supplied_test`. Mock-vs-prod divergence has burned us.
```

«Ловится: правило всегда в контексте → PR-ревью @claude → ревью человека.
Lint-правила пока нет.»

### Фаза system design (сл. 37-38)

- Никакого кода до утверждённого дизайна
- Дизайн-док: подход, файлы, модель данных, Mermaid-диаграмма
- Публикуется ссылкой, в тикете короткое резюме
- «Тикет слишком маленький для дизайна» не оправдание

Сл. 38: Drafting → «дизайн опубликован» → AwaitingApproval → «комментарии
человека» → Revising → «та же ссылка, новая ревизия» → AwaitingApproval;
AwaitingApproval → «утверждено» → Approved.

### Движение назад (сл. 39)

| Отклонено на этапе | Возвращается в | Что переносится |
|---|---|---|
| Проверка DoR | blocked_on_user | вопрос и твой ответ, в треде |
| Ревью дизайна | Designing | та же ссылка на дизайн, новая ревизия |
| Верификация | Implementing | упавшая команда и её вывод |
| Ревью PR | Reacting | комментарии ревью → follow-up коммит, та же ветка |

### Где живёт состояние (сл. 40)

- Диаграмма это состояние тикета в пайплайне, отдельно от статуса в Linear
- Один файл состояния на фабрику: `autopilot-state.json` на beast
- Одна запись на тикет: этап, worktree, ссылка на дизайн, PR
- Один тред на тикет в дашборде: вопросы, ответы, скриншоты
- Пишет его фабрика. Ты действуешь через тред.

### Флоу фабрики (сл. 19, 41, 42)

Сл. 19 «Текущий флоу»: Тикет → магия ✨ → Продакшен.

Сл. 41 «Итоговый флоу»: Разработчик пишет тикет · Фабрика проверяет DoR ·
Проектирует решение · Итерирует по фидбеку · Проверяет реализацию · Открывает pull
request'ы · Запускает авто-ревью и отрабатывает комментарии · Изменения в
продакшене.

Сл. 42 «Итоговый флоу как стейт-машина» (Mermaid):

```
[*] → Планирование {
  Discovered → DoRCheck
  DoRCheck —не готов→ BlockedOnUser —ответ→ DoRCheck
  DoRCheck —готов→ Designing ⇄ AwaitingApproval (фидбек)
}
Планирование —утверждено→ Разработка {
  Implementing → Verifying —проверки упали→ Implementing
  Verifying —проверки прошли→ PROpen
  PROpen —комментарии ревью→ Reacting —follow-up коммит→ PROpen
}
Разработка —смёржено→ Done → [*]
```

### Autopilot на beast (сл. 43)

- Домашний сервер, systemd-таймер и Claude Code в headless-режиме
- Просыпается каждый час или сразу по вебхуку из Linear или GitHub
- До 3 тикетов в работе, тикет на паузе держит свой слот
- Один git worktree на тикет

Схема: Комментарий в Linear / Ревью PR в GitHub → «Приёмник вебхуков, проверка
HMAC» → сервис autopilot ← «Таймер раз в час»; autopilot → Claude Code headless →
Worktree на тикет → Draft PR; Claude Code headless ⇄ «Дашборд-оркестратор + пуш на
телефон».

### Верификация и тесты (сл. 44-45)

Сл. 44: исполнитель никогда не оценивает свою работу сам; отдельный верификатор
заново запускает сборку, линт, тесты и миграции; изменения UI — настоящий браузер
через Chrome DevTools MCP, скриншоты в треде тикета; «Провал → обратно в
реализацию, а не к человеку».

Сл. 45:
- Локально на beast, в собственном git worktree тикета. Без общего стенда.
- Копируется .env, локальный Postgres, миграции применены и проверены
- Интеграционные тесты в контейнерах: Postgres, DynamoDB Local, S3Mock, Valkey
- UI: поднять стек тикета из дашборда, проверить в настоящем браузере
- Что это делает возможным: всё запускается из env-конфига с локальными backing
  services

### Цикл ревью (сл. 46, sequence-диаграмма)

Фабрика → GitHub: открыть draft PR; Фабрика → GitHub: «@claude please review»;
GitHub → Claude-ревьюер: запустить ревью; Claude-ревьюер → GitHub: комментарии
ревью; GitHub → Фабрика: вебхук; Фабрика → GitHub: follow-up коммит; Человек →
GitHub: approve + merge.

### Human in the loop (сл. 47-48)

- Один тред на тикет в дашборде, а не 40 комментариев в Linear
- Linear для фабрики только на чтение
- Вопросы и «PR готов» приходят пушем на телефон
- Утвердить, ответить или «fix now» из одного места

Сл. 48: Тикет → «Ты: отвечаешь на вопросы DoR» → «Ты: утверждаешь дизайн» → «Ты:
ревью PR + тест» → Смёржено. «3 точки контакта, каждая приходит пушем»; «Контекст
хранится в треде, помнить тикет не нужно»; «WIP-лимит: 3 тикета в работе».

### Где мы облажались (сл. 49)

- Выбегали из лимитов и фабрика простаивала
- Верили отчёту фабрики об «успехе». Всегда проверяй по GitHub и Linear.
- Тихие падения: таймер так и не включили, запуск из вебхука отклонил polkit
- Экранирование markdown в shell: падение №1. Сериализуй через JSON.
- Фидбек упирался в ёмкость очереди: реальный ответ в PR ждал 2 дня
- В headless-режиме нет Artifacts. Дизайн-доки переехали в gist'ы.

### Итоги (сл. 50-51)

- Ключ в итеративных улучшениях
- System Design и Product Management это ваша ценность
