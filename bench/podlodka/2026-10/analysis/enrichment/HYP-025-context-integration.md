## Что добавить в гипотезу

1. **Режим «read-only агрегатор» как явное ограничение v1.** Создание/правка задач и страниц исключена; совпадает с рисками гипотезы (ИБ), но там это не сформулировано как дизайн-решение.
2. **Второе направление: context -> draft tickets.** Агент готовит черновики задач (BRD + тред + выгрузка из БД), человек подтверждает. В гипотезе сейчас только «код -> почему».
3. **Slack-расширение переосмыслить:** отсюда же сценарий «тред с багом + БД -> задачи». Объединить с разделом Slack MCP.
4. **Решение build vs buy по MCP:** готовый официальный Atlassian MCP (Cloud) vs sooperset/mcp-atlassian (в т.ч. Data Center) vs свой скрипт на REST. В гипотезе только сырые REST-эндпоинты.
5. **Метрики.** «>80% точности диагноза» и «<30 с» без определения истины и перцентилей; добавить категорию «контекста нет» (подтверждено раньше доклад Бондаренко: L3), p95 латентности, долю ссылок на несуществующие ключи.
6. **Права:** один раз прописать, под чьим принципалом работает агент (пользовательский OAuth, а не сервисный ключ).

## Расконсервировать или нет

**Расконсервировать частично (статус active, но урезанный scope).** Обоснование:
- Технический барьер «нужен свой код под REST» исчез: Atlassian Rovo MCP GA с 2026-02-04, плюс open-source альтернатива. Шаг 3 гипотезы («написать CLI») больше не нужен как есть.
- Два независимых свидетельства (Бондаренко 16.09, этот стол) сходятся: ценность в read-only агрегации; в практике команд это уже рутина.
- Дёшево проверить: Шаг 1 гипотезы (ручная проверка на одном компоненте) стоит часа.
- Но: гипотеза привязана к avito-mobile (корп. токены, ИБ); без согласованного доступа остаётся DEFERRED. Условие запуска: токен/OAuth и разрешение ИБ. Без них расконсервация формальна.
- Простой замер на 5-10 компонентах с «контекста нет» как законным ответом решает, стоит ли дальше.

## Челлендж (gpt-5, роль скептика)

Выжило:
- **Агент сам создаёт задачи — антипаттерн (#5, #7).** Обязательные поля, валидаторы, ретраи при 429/5xx порождают дубли; у Jira нет idempotency-ключей на создание (утверждение моделью, не проверено по докам). Совпадает с позицией стола: автономный коммит не отдавать. Решение: агент готовит черновик, человек жмёт.
- **Метрики гипотезы несостоятельны (#8).** Нет определения истины, «<30 с» без p95, холодный auth и fan-out. Исправлено в разделе «Что добавить» п.5.
- **Права/принципал (#2) — условно.** Для OAuth на пользователя Atlassian заявляет доступ по правам пользователя, так что «утечка» для этого пути неверна; для API-токена/сервисного ключа риск реален и теряется аудит по человеку.
- **Git blame -> ключ задачи хрупок (#6).** Squash/cherry-pick/hotfix без ключа; агент может выдумать ключ. Нужна проверка существования ключа и режим «не найдено». Тоже из скептика, но логично и без внешнего подтверждения.

Отклонено / не подтверждено:
- #4 «pass@1 52.6% / pass^4 33.9% невозможно» — неверно: pass^k = все k запусков успешны, убывает с k; это строже pass@1 (скептик спутал с pass@k). Но замечание, что бенчмарки не про Jira и про модели 2025, справедливо.
- #1 (лимиты «убивают» <30 с) и #3 (качество CQL, лаги индексации) — без источников; единственная опора — один репорт про 429. Оставить как гипотезы для проверки на пилоте, не как факты.
- #9 «OAuth 2.1 расплывчато» — Atlassian в доках указывает OAuth 2.1; скептик опирался на память о 2.0.
