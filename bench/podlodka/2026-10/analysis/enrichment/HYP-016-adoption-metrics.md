## 3. Внешний ресёрч (Perplexity, 2026-10-12)

Adoption / retention (корпоративные):
- JetBrains survey, янв 2026 (через вторичные пересказы): workplace adoption Copilot 29%, Claude Code 18% (3% весной 2025), Cursor 18%; в стартапах <50 чел Claude Code 75%, Cursor 42%. Это доля «использует на работе», не частота и не retention.
- Accenture (вторично, axis-intelligence): Copilot установили в 1-й день 81.4%, 5+ дней/нед пользуются 67% - сильно расходится с «20-25% на постоянке» Подлодки; это один подбор/выборка.
- «90-day retention Cursor 78%, Copilot 64%» (wantsvibes.online) - методология не раскрыта, считать недостоверным.
- Вывод: публичных сопоставимых DAU/WAU/retention по корпоративным раскаткам нет. Число 20-25% ни подтверждается, ни опровергается; Perplexity сам рекомендует воронку seats -> activated -> WAU -> 30/90-day retained.
- Stack Overflow 2025: 47.1% используют AI ежедневно, 17.7% еженедельно, 13.7% реже (https://survey.stackoverflow.co/2025/ai). Это самоотчёт, и он заметно выше «не все даже раз в неделю» из эфира - пузырь у обеих сторон.

Частота vs результат:
- METR RCT 2025: 16 опытных разработчиков, 246 задач, +19% времени с AI при ожидании -24% и послеоценке -20% (https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/). Разрыв «ощущение vs измерение». Ранние инструменты, узкая выборка.
- Faros 2025 (10k+ разработчиков): +21% задач, +98% PR, но review time +91%, размер PR +154%, баги +9%, без org-level выигрыша (https://www.faros.ai/blog/ai-software-engineering). Ассоциация по группам, не дозозависимость.
- DORA 2025: ~90% используют AI; связь с throughput положительная, со stability отрицательная (https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report). Причинность не доказана.
- Ни один источник не показывает, что чаще у отдельного человека = лучше результат.

Личная аналитика:
- WakaTime (код по проекту/языку/редактору), RescueTime (приложения/сайты), Claude Code OpenTelemetry (стоимость, токены, строки; метрики могут быть дельтами интервала), ccusage (CLI-сводка). Рекомендация источника: не использовать токены, строки, время в редакторе как самостоятельную меру продуктивности; по реактивности - классический Hawthorne сильно преувеличен, но эффект измерения в self-tracking реален (стрик-накрутка).

## 4. Челлендж (gpt-5, роль скептика), что выжило и что нет

Выжило (применимо к Sergey):
- Vanity: частота/сессии/токены не равны ценности; METR и Faros - прямые примеры, где активность растёт без выигрыша. Проверка: связать с исходом на уровне item.
- «20-25% - норма» не доказано: без cohort-анализа по задачам это может быть плохой онбординг/доверие. Для Sergey не релевантно напрямую (он power-user), но для любой переноса на команду - да.
- Нулевая вариация: у ежедневного пользователя частота как метрика бесполезна (проверка: CV по дням; если мала - выкинуть).
- Self-report vs факт: оценка «энергия 8/10» и «AI сэкономил время» систематически врёт (METR +20% vs -19%). Нужна калибровка: оценка до/после против секундомера на выборке задач.
- Множественные сравнения и n=1: перебор «сон x встречи x AI x продуктивность» даст ложные корреляции -> предрегистрация 3-5 гипотез + FDR; без рандомизации (недели AI-first vs AI-after) причинность не доказать.
- Единица «сессия» нестабильна (таймауты, компакт, resume меняет sid) - агрегаты по sessions-db надо нормировать, проверять на дубликаты по цепочкам продолжения.

Отклонено/ослаблено:
- «Частота вредна, т.к. стимулирует дробление, A/B с окнами без AI»: для одиночки без внешней KPI-давления Goodhart слабый (он сам не награждает себя за счётчик); A/B-окна без AI дорого и ломают работу. Оставить как опцию, не как требование.
- Предложенный DORA-пакет, lineage prompt->prod, uplift modeling, ARIMA/BSTS: перебор для n=1; размер эффекта потонет в шуме.
- «Новичок спамит, senior редко» (возражение 9) - гипотеза без данных, не подтверждена ресёрчем.
- Приведённые скептиком метрики «value density >1» и «hallucination-induced bug %» требуют ручной разметки; на практике невыполнимы без дисциплины - не брать.
- Также: Hawthorne для self-tracking по ресёрчу сильно преувеличен; реактивность реальна, но как «накрутка стрика», что лечится не показыванием счётчика себе.

## 5. Итог: что мерить у себя, если частота не годится

Частоту оставить только как служебный счётчик нагрузки (дни без сессий = сигнал отпуска/сбоя, не KPI). Мерить:
1. Исход сессии: закончилась ли артефактом (коммит, закрытая задача TASKS.md, принятый документ) - доля таких сессий за неделю.
2. Переделка: сколько сессий/минут ушло на исправление результата предыдущей (сессии-продолжения на одну задачу, откаты git, повторные правки одного файла).
3. Стоимость на результат: токены/$ на принятый артефакт, не токены/день.
4. Калибровка (дёшево, 10-15 задач): до задачи оценить «с AI выйдет за X мин», после записать факт; смотреть среднюю ошибку. Это единственное, что бьёт по METR-ловушке.
5. Здоровье из исходной HYP-016 (сон, энергия) - как есть, но только 3-5 предзаявленных вопросов и недельные срезы; энергию мерить одним числом в конце дня, не пересматривать.
