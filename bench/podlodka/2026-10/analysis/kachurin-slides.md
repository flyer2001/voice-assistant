## Блок 1. Выбор модели (сл. 7-14)

**Тезисы**
- Платим за **решённую задачу**, а не за токен. Три оси выбора (сл. 7): сколько модель думает над задачей, стабильность кеша и эффективная цена input, возможности модели и цена дополнительных функций.
- **Сл. 8 «Модель дешевле — задача дороже»:** Lite думает, дважды ошибается, потом пишет код, итого **$0.08**. Smart думает и сразу пишет код, итого **$0.04**. «Слабая модель больше думает, ошибается и повторяет».
- **Сл. 9 «Разная скидка и стабильность кеша»:** модель с более дорогим input выигрывает за счёт скидки и hit rate (таблица чисел ниже).
- **Сл. 10:** фичи провайдера (Web Search, File Search, Compaction) стоят денег. Модель A дорогая с дешёвыми фичами, модель B дешёвая с дорогими фичами, модель C дешёвая без готовых фич.
- **Сл. 11 «Выбираем грейд, а не модель»:** Lite / Balanced / Smart. Логотипы: Lite — DeepSeek и Mistral, Balanced — Google и «K», Smart — Claude и OpenAI.
- **Сл. 12 «Каждая копейка на счету»:** разница в один цент на запросе на масштабе даёт $30k в месяц.
- **Сл. 13, BYOK:** (01) свой API-ключ пользователя к OpenAI, Claude, Grok, Gemini, с пометкой «Как сложно… я ведь даже не настоящий разработчик»; (02) подписка пользователя через «Sign in with OpenAI» → «Allow Reforma to use your ChatGPT subscription».
- **Сл. 14, выводы:** считать стоимость решённой задачи с reasoning, повторами и числом вызовов; выбирать грейд по сложности; учитывать кеш и платные tools; подключать доступ пользователя («снижают расходы почти до нуля»).

**Архитектурные решения:** алиас-грейды вместо имени модели (затем реализовано в Gateway, сл. 59). Модель подключается через ключ или подписку пользователя.

**Компромиссы:** дешёвая модель проигрывает на повторах. Дорогая модель с хорошим кешем выигрывает на input. Фичи провайдера экономят код, но стоят денег и привязывают к провайдеру.

## Блок 2а. Кеш и стабильный префикс (сл. 15-25)

**Тезисы**
- **Сл. 15 «Cache miss делает задачу в разы дороже»:** `gpt-6.1-sol`, один ход, контекст 200k. Вызов A: 90% cache hit (20k input + write, 180k cached) стоит **$0.108**. Вызов B: 10% cache hit (180k input + write, 20k cached) стоит **$0.812**. Разница «x7.5 дороже».
- **Сл. 16, почему кеш не работает:** (1) кеш не включён, или провайдер его не поддерживает; (2) boundary стоит не там: он должен отделять стабильный префикс от меняющейся части; (3) префикс короче минимального порога провайдера; (4) TTL истёк до следующего похожего запроса.
- **Сл. 17-18:** implicit cache — совпадающий префикс даёт hit автоматически. Explicit cache — метку ставите сами: boundary после system + tools или boundary на выбранном сообщении.
- **Сл. 19, теряется кеш при правильной настройке:** (1) смена модели или inference-роута, в том числе внутри одного провайдера; (2) динамический system prompt (время, контекст пользователя); (3) изменился набор tools; (4) sliding window обрезает начало истории.
- **Сл. 20:** «Изменение одного токена в system ломает весь префикс». Пример: Opened file, Mode, Branch и Time в system.
- **Сл. 21 «Динамику добавляем в конец»:** пользователь видит «Исправь failing test», а модель получает `<user_query>…</user_query><context>Current time, Opened file, Git branch, Pending todos</context>`. Fallback: если mid-turn system запрещён, `<context>` добавляется в копию user message.
- **Сл. 22-23:** напоминание → вызов инструмента → результат (пример: «У тебя есть 3 не закрытые задачи… используй GetTasks»). Подмешивание контекста по ключевым словам: Project Memory находит design-tokens.md и ui-guidelines.md и вставляет их как `<memory>` в сообщение пользователя.
- **Сл. 24 Skills:** в базовом контексте лежит короткое описание, полный `SKILL.md` загружается tool-вызовом `read_skill("design")` по требованию.
- **Сл. 25, выводы:** проверять hit rate, boundary, TTL и минимальный префикс; не менять модель, system, tools и старую историю без причины; динамику класть в хвост; знания грузить по требованию.

**Архитектурные решения:** замороженный префикс (system + tools). Всё изменчивое уходит в хвост, в user message. Знания загружаются лениво (reminder → tool/skill).

**Компромиссы:** свежесть system prompt против сохранности кеша. Смена модели посреди сессии обнуляет кеш, и это прямая цена роутинга.

## Блок 2б. Сжатие истории (сл. 26-35)

**Тезисы**
- **Сл. 26 «Лимит контекстного окна»:** шкала от 0 до 200k. Зона «кеш ещё выгоднее сброса» идёт до ~120k, «точка пересмотра» от 120k до 200k. Три причины: **дороже** («даже cached input продолжает стоить денег. После порога выгоднее начать новый контекст»), **медленнее** (prefill), **хуже качество** («слабые модели начинают забывать детали… галлюцинировать»).
- **Сл. 27, четыре способа:** Trim (последние N, мгновенно и бесплатно, code path), Microcompact (структура без шума, без LLM, code path), LLM summary (лучшее качество, но latency, model path), Provider summary (минимум кода, model path).
- **Сл. 28:** UI не меняется, а между сообщениями хранится скрытый объект `<summary>`. В запросе к модели он идёт system-сообщением.
- **Сл. 29 Trim:** m1-m8 → оставили последние 4.
- **Сл. 30 Microcompact, «до 90% контекста — мгновенно, детерминированно и бесплатно».** На схеме: текст ассистента KEEP; Read, Bash, Screenshot, attachment и Status — DROP; Write — SHRINK (до «token.ts +N −N»); Search проходит через «JEV decision: useful for current task?» и получает KEEP; последние 4 сообщения не трогаются.
- **Сл. 31 LLM Summarization:** «Формат summary задаём сами». Три варианта: (1) дешёвое саммари по запросу или при новом сообщении: сначала микрокомпакт (убрать старые сообщения, аттачменты, reasoning, шумные инструменты), затем дешёвая модель без reasoning, на схеме подпись ≈$0.01; (2) саммари посреди работающего цикла при >200K контекста: префикс уже в кеше, саммари делает текущая модель; (3) сжатие на стороне провайдера (OpenAI) → `summary_id`. Шаблон summary: Primary request and intent; Continue here (Active task, In flight, Done vs not, Next step, Do not redo); Key technical concepts; Files and code; Errors and fixes; User constraints and preferences; Pending tasks.
- **Сл. 32 «Минусы сжатия»:** если сжать посреди активной задачи, «модель может забыть работу и начать восстанавливать контекст». Пример из интерфейса: «Explored 15 files, 13 searches» → Chat context summarized → «Exploring 16 files, 9 searches, 6 tools». Второй пример: 17 files / 9 searches → summarized → 14 files / 7 searches. После сжатия агент заново исследует примерно тот же объём.
- **Сл. 33, пороги.** На новом сообщении пользователя: **>50 messages / 60k** → microcompact; **>120k / 30min+** → microcompact («старый чат: шанс cache hit почти нулевой»); **>160k** → LLM summary («жирный контекст: дальше гонять невыгодно»); `/summarize` запускается вручную. Между tool calls: **200k+ EMERGENCY**, сжимаем немедленно, даже если ход не закончен.
- **Сл. 34 «Точка сброса состояния»:** «Кеш уже потерян. Используем этот момент, чтобы пересобрать всё динамическое окружение»: Caches stale → fresh, System prompt outdated → fresh, MCP/Plugins list outdated → fresh.
- **Сл. 35, выводы:** сначала microcompact; LLM summary только по порогу, внутри agent loop только аварийно; после сжатия задача продолжается, а сам момент используется для пересборки состояния.

**Архитектурные решения:** сжатие привязано к границе хода пользователя, а не к середине цикла. Сжатие совмещено с пересборкой system, tools и MCP, раз кеш всё равно сгорел. Фильтр «полезно ли для задачи» (JEV) ставится только на спорные вызовы.

**Компромиссы:** сжатие посреди задачи бьёт по качеству (повторное исследование, сл. 32). Сжатие на пороге хода бесплатно с точки зрения кеша. LLM summary точнее, но медленнее. Provider compaction требует меньше всего кода, но привязывает к провайдеру.

## Блок 3а. Набор инструментов (сл. 36-42)

- **Сл. 37 «10+ инструментов — налог на каждый ход»:** схемы лежат в system prompt и передаются на каждом ходе. Следствия: раздувается контекст, модель теряется в выборе среди похожих tools, а MCP «превращает 50 tools в сотни».
- **Сл. 38 ToolSearch:** в префиксе остаются System instructions, ToolSearch и список namespaces (GitHub, Docs, Design). Найденные определения (GitHub.create_issue, GitHub.search_issues) попадают в хвост, префикс не меняется.
- **Сл. 39, динамическая смена active tools:** код `generateText({… prepareStep: activeTools: isBashLoaded ? [...] })`. Run 1 идёт с Read/Edit, Run 2 с Read/Edit/Bash. Новый список «переписывает system prompt и инвалидирует весь prefix». Это показано как антипаттерн.
- **Сл. 40, экспериментально — tool обычным текстом:** схема описывается в message, модель генерирует tool call, SDK падает («tool не объявлен»), repair handler `recoverToolCall()` проверяет registry, и вызов исполняется вручную.
- **Сл. 41, два meta-tools:** `GetDynamicTools(namespace?)` и `CallDynamicTool(namespace, tool, args)`. В замороженном префиксе только namespaces (figma, linear, github). Runtime MCP registry, «tools can change».
- **Сл. 42, выводы:** держать постоянно только необходимое. Если привязаны к провайдеру, использовать серверный ToolSearch. Если нужна независимость и MCP, писать свои meta-tools.

**Компромисс:** серверный ToolSearch проще, но привязывает к провайдеру. Meta-tools независимы, но держатся на обходе SDK (сл. 40 помечен «экспериментально»).

## Блок 3б. Результаты инструментов (сл. 43-56)

- **Сл. 44 «Инструменты это бóльшая часть истории»** (подпись: «пример объёмов output»): Bash (логи тестов) +18k, Read (файл целиком) +35k, Fetch (страница целиком) +200k, Edit (input + diff) +48k. Накопительно 18k → 53k → 253k → **301k за 4 вызова**. «Один неосторожный вызов и его output остаётся с агентом до сжатия».
- **Сл. 45-46:** в UI уходит одно, в модель другое. `editFile` возвращает `{diff, added, removed}` для интерфейса, а `toModelOutput` отдаёт только `added/removed`. Для картинки текстовое описание («красная двухдверная машина») сравнивается с передачей самого файла по URL.
- **Сл. 47:** сырой output тестов 18k tok → фильтр failures only → **700 tok**.
- **Сл. 48-49 Rust Token Killer:** переписывает команду (`git status` → `git status --porcelain -b`) и сжимает вывод: `cargo test` на 1 842 строки → 3 строки («184 passed · 0 failed · 3 ignored»).
- **Сл. 50 Fetch:** 260 KB HTML ≈ **100k tokens** → mdream → 3 KB Markdown, **800 tokens** → LLM Filter → **250 tokens**.
- **Сл. 52 Context7:** вместо цепочки Search → Fetch идут resolve-library-id и query-docs и возвращают нужный фрагмент. «140k+ проиндексированных библиотек».
- **Сл. 53 «Поиск по смыслам»:** Glob/Grep заменяются индексом кодовой базы (CodeGraph, codebase-memory, mgrep, gortex). **412k → 3,4k токенов, ≈120× меньше**, подпись «5 структурных запросов · benchmark авторов».
- **Сл. 54, субагенты:** основной агент вызывает `Research(...)` («лёгкая модель + минимум tools»). Вся рабочая история (Search, Read, Fetch) остаётся в субагенте, обратно возвращается «только итог».
- **Сл. 55, параллельные tools:** «Output не уменьшается, но контекст перечитывается меньше раз». Последовательно: 6 ходов по 50k контекста, ≈330k input. Параллельно (Write A/B/C, затем Verify A/B/C): 2 хода, ≈130k input, **−200k input**.
- **Сл. 56, выводы:** модели отдавать минимально необходимый результат, а сырые данные хранить отдельно; исследование выносить из основного контекста (индексы, точный поиск, субагенты); независимые tools запускать параллельно.

**Архитектурные решения:** у каждого инструмента два выхода, для UI и для модели. Перед попаданием в контекст стоят фильтры и сжатие. Исследование делегируется субагенту.

**Компромисс:** на слайдах нет цены потерянной информации, то есть нет ответа на возражение Марины (ниже).

## Блок 4. Gateway (сл. 57-64)

- **Сл. 57:** Model Gateway = LiteLLM / OpenRouter. Задачи: унификация запросов, подсчёт стоимости, логирование.
- **Сл. 58, подсчёт стоимости сессии `s_42`:** генерация заголовка — GPT, 1 вызов, **$0.002**; основной агент — Gemini, 10 вызовов, **$0.128**; Research — DeepSeek, 5 вызовов, **$0.030**. Всего 16 вызовов, итого **$0.160**. Webhook в Billing API: у user_42 было 200 credits, стало 184.
- **Сл. 59, один API и routing table по алиасам:** lite — DeepSeek 4.1-flash, fallback GLM 5.3-flash; balanced — Gemini 3.8, fallback gpt-6.1-sol; smart — grok-4.7, fallback gpt-6.1-sol. Запрос `model: "balanced"` → выбрано Gemini 3.8, «код агента не изменился».
- **Сл. 60:** таблица провайдеров OpenRouter для одной модели (название не видно): input $0.21-$0.30, output $0.84-$1.20, cache $0.0042-$0.03, uptime 98.43-100%. Сигналы для роутинга: price, latency, failure rate, cache hit.
- **Сл. 61:** серверные tools OpenRouter, доступные любой модели: Web Search, Datetime, Image Generation, Web Fetch, Apply Patch, Shell, Bash, Fusion, Advisor, Subagent, Search Models, Tool Search, Files.
- **Сл. 62:** один MCP вместо десятка. Агент знает один endpoint («1 endpoint · 1 token»), а за MCP Gateway (API keys, Auth) стоят Context7, Google Maps, GitHub.
- **Сл. 63, toolsets:** filter — у Google Maps MCP оставлены search_places и place_details, убраны weather и routes («2 полезных tools вместо 4»). Bundle — Context7 query-docs, GitHub search-code и Perplexity search/research собраны в «Research toolset».
- **Сл. 64, выводы:** Gateway берёт на себя стоимость каждого пользователя, один API, модели без релизов, лучший inference endpoint, серверные tools и MCP toolsets.

**Компромисс:** на сл. 60 прямо видно, что роутинг по провайдеру выбирает inference. По сл. 19 это ломает кеш («разные модели и роуты могут уходить на разные inference — общего кеша между ними нет»). Внутри доклада это противоречие не разрешено: cache hit назван одним из сигналов роутинга, но как держать кеш при переключении провайдера, не сказано.

## Итог (сл. 65)

«Не один приём, а вся цепочка от запроса до результата»: (1) считаем весь agent loop, модель под сложность; (2) контекст стабильный — cache hit, стабильный префикс, сжатие по порогу; (3) tools не создают шум — tools и знания по требованию, сжатый output, субагенты; (4) Gateway забирает обвязку — billing, ключи, routing, MCP-фильтры и toolsets.

## Что отвечает на вопросы Sergey'я

**1. Доля стоимости по компонентам агента — замера нет, только иллюстрации.**
- Сл. 58 (пример сессии): основной агент $0.128 из $0.160 (**80%**), Research-субагент $0.030 (**19%**), генерация заголовка $0.002 (**1%**) [расчёт].

- Разбивки «system / tools-схемы / история / output» в деньгах на слайдах нет. Есть только ценовые кратности сл. 6 (output 5x, cache write 1.25x, cached 0.1x).

**2. Выигрыш от кеша в % — только расчётные примеры, без продакшен-hit-rate.**
- Цена: cached = **−90%** к input (сл. 6, сл. 9 Model 2), −75% (сл. 9 Model 1).
- Effective input при реальном hit rate: **−60%** (80% hit, −75%) и **−85,5%** (95% hit, −90%) [расчёт по сл. 9].
- Один ход 200k на `gpt-6.1-sol`: 90% hit против 10% hit = **в 7,5 раза** дешевле, $0.108 против $0.812 (сл. 15).
- Какой hit rate у Reforma на деле, не сказано.

**3. Когда компакт хуже честного рестарта — прямого сравнения нет, есть три косвенных правила.**
- **Посреди задачи компакт плох.** Модель «может забыть работу и начать восстанавливать контекст»: 15 files / 13 searches → после сжатия снова 16 files / 9 searches (сл. 32). Внутри agent loop — только аварийно при 200k+ (сл. 33, 35).
- **После ~120k «точка пересмотра»** (сл. 26): «даже cached input продолжает стоить денег. После порога выгоднее начать новый контекст». Здесь он сравнивает с **новым контекстом**, а не с компактом. Где граница компакт/рестарт, не сказано.
- **Когда кеш уже мёртв** (>120k и 30+ мин простоя, сл. 33), компакт ничего не стоит в кеше, и момент используется для пересборки system, tools и MCP (сл. 34).
- Цифр качества (ошибки, переделки) после компакта и после рестарта нет.
