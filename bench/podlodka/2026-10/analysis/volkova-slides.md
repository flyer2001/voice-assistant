## Архитектура

### Части и компоненты (сл. 18-20)

- **Сл. 18, части:** чат в мессенджере («там, где общается команда»); бекенд-агент («инструменты до внутренних
  ресурсов»); CLI-агент («для кодинга»); админка (настройки пользователей); веб-чат (браузер и Chrome-плагин).
- **Сл. 19, схема:** вход в бекенд тремя путями: user через Web Chat (**AG-UI websocket**), **trigger**, **API (async)**.
  Внутри «Tihon backend (k8s)»: **Master agent** ↔ **Sub-agents** (Delegate / Report). Master пишет **plan** (Update)
  и вместе с сабагентами читает/пишет **ad-hoc memory**. Хранилище: **DB (postgres, redis)**. Наружу: LLM; **CLI agent
  по A2A**; через общий узел к IAM, Bank systems, MCP.
- **Сл. 20, слои ядра (сверху вниз):** State Machine → Graph Behavior Layer → Domain Objects Layer → Provider
  Transport Layer. «Одно ядро, Java + Spring»; бекенд-агент сервис в k8s; CLI-агент в изолированной среде.
- **Сл. 21, модель данных:** `sealed interface LLMMessage permits User, Assistant, ToolCall`; `Assistant(content,
  reasoning)`; `ToolCall(ToolCallRequest request, String response)`, то есть вызов и ответ тула хранятся одной записью.
- **Сл. 22, граф:** «кастомный граф-движок, каждый узел одно действие, легко добавлять новое поведение». Рёбра:
  start → llmCallNode; llmCallNode → toolExecutionNode `ifToolCall`; toolExecutionNode → llmCallNode `ifNextCycle`;
  llmCallNode → end.

### State machine (сл. 25-29)

**Проблема (сл. 25):** сессия агента может занимать часы; бекенд иногда уходит в редеплой/рестарт; долго держать
graceful shutdown нельзя. **Решение:** агент неблокирующий, состояние сохраняется «в безопасных точках», работа
продолжается на новом контейнере без потери данных.

**Сл. 26, где checkpoint:** цикл запрос в модель → модель отвечает тул-коллами → вызываем тул-коллы → добавляем в
историю. Крупно «**ЗДЕСЬ!**» стоит на дуге между «добавляем в историю» и «запрос в модель». Мельче «или здесь?» на дуге
между ответом модели и вызовом тулов. Вывод: точка сохранения выбрана после записи результатов тулов в историю, до
следующего запроса в модель.

**Сл. 27, «ИИ-Агент как state machine».** Состояния:

| Из | Событие | В |
|---|---|---|
| (старт) | | IDLE |
| IDLE | FYI | IDLE (петля) |
| IDLE | chat | BUSY |
| BUSY | need approval / remote tool call / subagent | WAIT |
| WAIT | not all results | WAIT (петля) |
| WAIT | tool result / tool approved | BUSY |
| BUSY | (пунктир) | drain |
| drain | poll | BUSY |
| drain | empty / paused | IDLE |
| any | cancel | IDLE |

Сбоку два хранилища: **Mailbox (вход-очередь)** пунктиром питает drain; BUSY пунктиром отдаёт в **Delivery (выход)**.

**Сл. 28, «Чекпоинты»**, граф одной итерации (зелёным выделены lock session, try release lock + check queue,
DrainMailboxNode):

- start → **lock session** → LLMCallNode
- LLMCallNode `ifToolCall` → ToolExecutionNode → **DrainMailboxNode**
- DrainMailboxNode `new commands` → LLMCallNode
- DrainMailboxNode `ifPause` → release lock → **save session** → конец
- ToolExecutionNode `ifDeferredToolCall` → release lock → save session → конец
- LLMCallNode `no more tool calls` → **try release lock + check queue**: `queue empty` → save session → конец;
  `queue not empty` → DrainMailboxNode

**Сл. 29, `AgentClient`:** `chat(sessionId, message)`, `fyi(sessionId, message)`, `toolResult(sessionId, toolCallId,
result)`, `cancel`, `pause(sessionId, Duration deadline)`, `resume`, `status` → `enum Status { IDLE, BUSY, WAIT }`.
Наружу видны три статуса, drain нет.

**Где живёт состояние.** На слайдах: сессию сохраняет узел `save session` (сл. 28), хранилище на этом слайде не
названо. На сл. 19 у бекенда DB **postgres, redis**, отдельно хранилища **plan** и **ad-hoc memory**. Какое из них держит
сессию, а какое lock, слайды не говорят. Вывод: сохраняется сессия агента (история + очередь входящих), снимается
lock, и любой контейнер может подхватить её следующим событием. Deferred tool call (удалённый вызов в sandbox) тоже
выходит через save session, поэтому бекенд не держит поток, пока CLI-агент работает; результат приходит callback'ом
(сл. 34) и, видимо, через `toolResult` (сл. 29). Связь callback ↔ `toolResult` моя, на слайдах стрелки нет.

### Работа с кодом и sandbox (сл. 31-37)

- **Сл. 31, «Агент тестирует»:** у агента есть инструменты, чтобы пересобрать и перезапустить себя; это используют для
  тестирования; CLI-агент тестирует backend по API, UI через Chrome MCP, есть MCP для дебага.
- **Сл. 32:** тулы read, write, replace, grep, glob, shell; пример `ReadFileTool` с `resolveAndValidatePath`.
- **Сл. 33:** код надо куда-то клонировать, на бекенд-контейнер нельзя, агент должен работать с кодом бесшовно. Решение:
  sandbox, то есть инфраструктура для контейнеров, CLI-агент завёрнут в Dockerfile, бекенд умеет вызывать sandbox.
- **Сл. 34:** Tihon backend (AGENT LOOP) → `start sandbox` → «Tihon CLI (**any A2A-compat**)», AGENT LOOP внутри
  «ML Core» с FILE SYSTEM, Local MCPs, Local skills → `callback` обратно. То есть в sandbox может стоять любой
  A2A-совместимый агент, не только свой.
- **Сл. 35-36, сквозной пример:** вопрос в треде про Jira-подписки → Тихон предлагает правку двух doc-файлов и спрашивает
  «создать MR через sandbox?» → через 32 минуты (1:36 → 2:08 PM) Draft MR !741, CI pipeline success (lint, build-site,
  build-gradle, unit-test, component-test). «MR создан как **Draft**. Нужно снять с draft и назначить ревьюера (правило
  quality → @Nadezhda Volkova)».
- **Сл. 37:** детерминированный клон репозитория и ветки; готовые скрипты установки runtime; мониторинг состояний
  sandbox, **таймаут неактивности 1 час**; Spec Driven Development, скиллы `github.com/obra/superpowers`.
- **Сл. 45:** задача PCAI-625 (label `vibecoded`, эпик «Sandbox - 2nd Iteration»): плагин в Docker-образе ставился под
  root, а sandbox работает под uid 2000, поэтому при первом вызове докачивал ~54 МБ на 62-197 kB/s (~14-15 мин) и падал
  по `TerminalTimeout PT30M`. Шаблон задачи: проблема, цель, тех. решение, ограничения, критерии приёмки.

### Безопасность (сл. 40-43)

«ИБ пришли по нашу душу» (картинка: «9 задач VULN, лето»). Сервис-аккаунт с широким доступом небезопасен, ключ от
каждого неудобен. Решение: **OAuth 2.0 Token Exchange (RFC 8693)**: получаем имя пользователя, запрашиваем его токен в
конкретную систему (audience), используем только его. Токены в Caffeine-кэше (10 000 записей, TTL 3600 с), «токен
ограничен в правах». Транспорт веб-чата (сл. 46): AuthN на handshake через oathkeeper, AuthZ по подписке, WebSocket STOMP
(run / cancel / iteraction [так на слайде] туда, delivery / visualisation events обратно), automatic reconnect, отдельно
Chats HTTP CRUD.

## Масштабирование (сл. 10, 12, 33-34)

Сл. 12 сравнивает три варианта для «хотя бы 500 человек»:

- **Локально:** дорого, долго, ненадёжно, «хочется чтобы "само"».
- **Облако, контейнер на каждого агента:** изоляция, но дорого, и непонятно, как сделать чат.
- **Бекенд:** дёшево, но открыты вопросы: длинные сессии, куда клонировать код, безопасность.

Выбран бекенд. Три вопроса закрываются тремя блоками доклада: длинные сессии решает state machine с чекпоинтами,
клонирование решает sandbox по вызову, безопасность решает token exchange. Вывод: контейнер поднимается только под
кодовую работу (sandbox, гасится по таймауту неактивности 1 ч), а разговорная часть живёт в общем k8s-сервисе.

## Связь с нашими гипотезами

- **HYP-052 (состояние вне контекста).** Состояние вынесено, но на другом уровне, чем у Быстрова и Codey. У Быстрова
  серверная стейт-машина **задачи** вне контекста агентов. У Codey Postgres с чекпойнтами **стадий задачи**
  (`codey-slides.md`). У RWB артефакты на ветке. У Волковой стейт-машина **сессии агента** (IDLE/BUSY/WAIT/drain) плюс
  чекпоинт на каждой итерации цикла. Цель не провести задачу по стадиям, а пережить редеплой и не держать поток во время
  долгого тула. Стадии SDLC-задачи (DoR → код → ревью → DoD) живут в Jira и в отдельных сценариях-триггерах (сл. 17),
  не в state machine. Ближе всего к 052 хранилище **plan** на сл. 19, но его обновляет сам Master agent, так что это не
  детерминированный контракт. Переносимое для нас: mailbox + drain, где сообщения пользователя посреди работы не
  прерывают цикл, а складываются в очередь и вычитываются в безопасной точке. Плюс FYI как отдельный тип входа,
  который не будит агента. Плюс pause с deadline.
- **HYP-047 (личная пропускная способность при многих агентах).** Слайды дают ход «агент живёт в командном чате и
  отвечает асинхронно» (Delivery, deferred tool call, MR приходит сообщением). Человек получает результат, а не
  сторожит окно. Против: «вайбкодинг увеличивает разрыв между простыми и сложными задачами», «полная автоматизация пока
  не работает» (сл. 50). Про нагрузку на человека цифр нет.
- **Codey/Быстров, вопрос «кто выносит вердикт».** У Волковой вердикт не автоматический: Draft MR + назначенный
  правилом ревьюер-человек (сл. 36); DoD-вердикт выносит сам Тихон текстом (сл. 17), и блокирует ли он что-то, не
  сказано.
